# Contributing to Alexander

Alexander should be easy to challenge, extend, and improve.

The repository is not meant to converge by making every file polished and agreeable. It should converge by making ideas easier to inspect, test, criticize, and build upon.

## Before changing something

Try to identify what kind of thing you are editing:

- a value
- a factual claim
- a prediction
- a policy proposal
- an implementation idea
- an experiment
- a metaphor or piece of art
- deliberately speculative nonsense

Different things deserve different standards.

A factual claim should become more verifiable.
A policy proposal should expose tradeoffs.
An experiment should define what would be learned.
A value may simply need to be stated clearly.
A metaphor should not be "corrected" into lifeless prose just because it is strange.

## Preserve signal

The existing voice is part of the project.

Do not automatically normalize spelling, grammar, profanity, religious imagery, dark humor, or unusual phrasing. Fixing text can destroy information about what the author was trying to express.

If a passage is confusing, prefer one of these approaches:

1. add a clearer companion passage
2. add context around it
3. propose a focused rewrite and explain what is gained and lost

## Prefer additive refinement

When possible, preserve the historical source and add a more developed version nearby.

This makes it possible to see how an idea evolved and reduces the risk that one editor quietly replaces the project with their own voice.

## Separate conviction from evidence

Strong values do not require weak epistemics.

When making empirical claims:

- link evidence when practical
- distinguish observation from inference
- state important assumptions
- include serious counterevidence
- avoid pretending precision that is not available

When making predictions, write them so reality can prove them wrong.

## Make disagreement useful

A good objection is a contribution.

Criticism should identify the strongest version of the idea being criticized rather than the easiest version to defeat.

When two principles conflict, document the conflict. Do not hide it with vague language.

## Prefer reversible action

For ideas that could affect real people, start with the smallest useful experiment.

A strong experiment says:

- what is being tried
- who is affected
- what success would look like
- what failure would look like
- what harms are possible
- how the experiment can be stopped or reversed
- what evidence will be published afterward

Scaling should follow evidence, not excitement.

## Keep power legible

New organizational mechanisms should make clear:

- who can decide
- who is affected
- how decisions can be challenged
- how conflicts of interest are exposed
- how leaders are replaced
- how authority ends

If a mechanism only works when the right person is in charge, it is unfinished.

## Pull requests

Prefer one coherent idea per pull request.

A useful PR description should answer:

- What problem does this address?
- Why does it fit the existing project?
- What changed?
- What assumptions does it make?
- What should reviewers disagree with or stress-test?

Large changes are easier to trust when they are assembled from small visible steps.

## Build things

The repository should not remain only words.

Software, experiments, simulations, research, media, organizational tools, and useful products are all valid contributions when they embody the values rather than merely advertise them.

The point of the text is eventually to make better things possible.
